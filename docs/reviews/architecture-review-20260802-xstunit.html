Problem —
TypeLayout is the declared authority on layout but its interface answers only how many bytes; the byte content rules leak into Engine, where PackValue/UnpackValue re-walk the same five type shapes and independently restate the array stride fold, the string +1 terminator and every scalar width.
Solution —
Move packing and unpacking behind the same interface as sizing, driven by the same Func<string,int> bound-resolver seam the constructor already takes. Engine.ByteLayout keeps only Cell⇄buffer adaptation and the Commit write-back.

▸ locality: layout bugs land in one module

▸ leverage: one walk, three consumers

▸ new IEC type = one edit, not three

▸ tests drop Engine, Frame and ST fixtures

Deletion test: yes — deleting Engine.ByteLayout's pack/unpack concentrates the rules rather than moving them. Today the only test of byte packing is MemIntrinsicsTests, which reaches it through MEMCPY in an ST fixture.

Sliced by type shape, not by direction — each child moves one shape through both pack and unpack and lands with a test needing no Engine. 08zk.1 (scalars + BOOL) is the tracer bullet and the seam everything else waits on.

Problem —
Pointer width is a layout rule that depends on the compile target, but TypeLayout takes no target and hard-codes 4 bytes. LayoutOracle picks the x64 declared width while asking TypeLayout for an x86 computed width, so every x64 module reports pointer-width findings that are an artefact of the seam, not of the rules.
Solution —
Give the layout module a target parameter (pointer width, and whatever else turns out to vary) alongside the registry. The oracle passes the target it read from the .tmc; the interpreter passes its own default.

▸ oracle measures rules, not the seam

▸ x64 SIZEOF becomes expressible

▸ target is a value, testable per case

▸ smallest diff of the six candidates

Answered already, no investigation needed: the tracker records the x64 mismatch as a known gap, not a disagreement about a rule — xstunit-229.31/.32 both state it, and 229.30's acceptance criteria already require the x64 diff to come clean.

Upgraded to a bug (xstunit-5i6j): the POINTER TO / REFERENCE TO prefix test is spelled three times with three different comparisons — TypeLayout.cs:85 (Ordinal), Engine.Defaults.cs:48 (OrdinalIgnoreCase), Engine.Cells.cs:121 (none, so culture-sensitive). A POU declaring pointer to BYTE gets a pointer default from Engine.Defaults, culture-dependent behaviour from __ISVALIDREF, and a refusal from TypeLayout. Gates 229.30 — single-source the predicate before its return value changes.

3 · The wire contract has no module

Strong in-process xstunit-e7vb · .1 .2
  • src/xStunit.Cli/CliRunner.cs (987 lines; Run = 434; DTOs = 350)
  • tests/xStunit.Cli.Tests/ (19 files, all end-to-end)
  • src/xStunit.Vsix/TestRunner/XstunitModels.cs (the other end of the same contract)

Before — one entry point, everything inside it

CliRunner.Run — the only public surface
arg parse · format validation · exit 2
POU / DUT / GVL load · dedupe · registry · suite filter
suite execution · broad-catch isolation
WriteError · ReportTests — local functions
text · json · NDJSON emit, ×3 at each site
11 private sealed class DTOs — the JSON contract, unaddressable

Every test constructs a StringWriter and asserts on stdout.

After — three modules, three test surfaces

CliRunner — parse args, orchestrate, exit code
Workspace load — dirs ⟶ registry + skips
POU · DUT · alias · enum · GVL · dedupe
Run report — the wire contract
public DTOs · guidance · text/json/NDJSON writers

NDJSON schema and guidance text get direct tests; end-to-end tests stay for the exit-code contract.

Problem —
The JSON and NDJSON output is a published contract — the VSIX parses it — yet it exists only as private classes inside a 987-line file, and its two formatters are local functions capturing asJson/streaming/three counters. Nothing behind that entry point can be reached by a test.
Solution —
Two modules out of Run: a workspace-load module returning the loaded set plus its skips, and a run-report module owning the DTOs, the guidance rules, and one writer per format. CliRunner keeps arg parsing, suite iteration, and the exit-code decision.

▸ the wire contract becomes a test surface

▸ one shape, three writers — not three inline

▸ VSIX models can share the seam

▸ locality: skip accumulation stops threading

Scope note: the comments in CliRunner.cs are unusually load-bearing — they record why the broad catch, the pre-scan, and the exit-code rules are what they are. Any split has to carry them, not drop them.

Problem —
Adding a new native host kind means editing a name set, ClassifyNativeHost, and an invocation switch arm. Loopback faults carry a second name set and a second switch. The TcUnit bridge has the hazard written into its own comment — “CanInvoke MUST stay in agreement with Invoke's dispatch below; the two are separate walks” — and while the scalar asserts are now registry-driven and test-locked, the prefix rules and two local sets are still hand-matched on both sides. Only the plugin registry is deep.
Solution —
Unify the three switch-based mechanisms behind one internal registry that can carry the FbInstance and Frame a host needs. Leave IXstunitNativeFunction exactly as it is.

▸ new host kind = one registration

▸ deletes a name set and two switches

▸ CanInvoke and dispatch stop diverging

▸ dispatch precedence stated once

Decided. The open question was whether to widen the plugin interface itself. Answer: no — IXstunitNativeFunction / NativeCallContext take pre-evaluated CLR values on purpose and are the only surface an outside plugin author writes against. Unify mechanisms 1–3 behind an internal registry; leave the public seam alone. No implementation bead filed until that lands as the bead's resolution.

5 · The TcUnit assert surface is spelled three times

Withdrawn xstunit-f3rb

Corrected — the headline was false. The consolidation already shipped. FB_TestSuite.AssertEqualsScalar (:262) is table-driven off ScalarAssertType.Registry, and each of the 19 AssertEquals_<TYPE> methods is a one-line forward into it. Top recommendation

1 · Give the layout module the bytes, not just the byte count

It is where the codebase is hottest — the last five commits all touch byte layout — and it is the only candidate that deepens a module the other candidates then build on.
