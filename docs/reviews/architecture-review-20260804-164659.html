Problem

The Engine owns the byte[] ↔ ArrayValue marshalling — four hand-written loops in 118 lines — and one layout fact: elementTypeName == "BYTE" (:24-26) decides the fast path by string compare, so SINT/USINT arrays — equally 1 byte wide per TypeLayout.cs:189-191 — silently take the repack path the comment at Engine.Expressions.cs:262-265 claims they avoid.

Solution

Move the marshalling and the fast path behind a ByteView module: Open(Pointer, Frame), indexer, Commit(). The fast path asks SizeOf(elementType) == 1 instead of comparing a name. Engine.ByteLayout.cs and Engine.SizeOf.cs collapse into the LayoutFor(frame) closure and nothing else.

Wins

  • Locality: byte semantics in one module
  • Four marshalling loops become one
  • 1-byte fast path covers SINT/USINT
  • Tests hit ByteView, not parsed ST
  • Interface shrinks; implementation absorbs it
  • Kills the shallow Engine.SizeOf.cs
Test surface today — ScalarByteCodecTests/StringByteCodecTests (372 lines) exercise TryPackScalar, TryUnpackScalar, TryPackString, TryUnpackString — zero production callers. The code that actually produces observable MEMCPY behaviour is reachable only through parsed ST in MemIntrinsicsTests. Extracted for testability; the bugs live in the caller.

2 · Move the layout oracle across the seam it measures

Strong local-substitutable
  • src/xStunit.Interpreter/Conformance/{LayoutOracle,LayoutFinding,LayoutReport}.cs (461 lines)
  • src/xStunit.Parser/Loaders/TmcLayoutReader.cs + the .tmc half of Ast/ModuleLayout.cs (~320 lines)
  • tests/xStunit.Interpreter.Tests/Conformance/*.cs (897 lines — the only consumers)

Before — oracle inside the thing it measures

After — oracle on the test side of the seam

Problem

grep -rn "LayoutOracle\|TmcLayoutReader\|LayoutReport" src/ returns nothing outside the definitions — no CLI verb, no runner path, no VSIX use. ~780 lines of test infrastructure compiled into two shipped assemblies. Because it sits on the production side, it has to fake production inputs: LayoutOracle.cs:230-233 builds "POINTER TO BYTE" strings from the .tmc's structured booleans purely so AddressTypeInfo.cs:32 can regex them apart again.

Solution

Move Conformance/ and the .tmc reader into a test project. The oracle then measures TypeLayout through its public interface, the way any other adapter would — the .tmc's structured shape goes straight into a StructAst with no string round trip.

Wins

  • Two shipped assemblies shed ~780 lines
  • Stringly round trip disappears
  • Two adapters justify the seam: ST source, .tmc
  • Naming collision on TargetPlatform resolves
  • Conformance/ stops needing InternalsVisibleTo
  • Locality: oracle lives with its golden files
Latent defect this exposes — TypeLayout.StringCapacityOf:473 catches InvalidOperationException, but on the _resolveBound == null path — exactly how LayoutOracle.cs:43 constructs it — ParseStringLength:526 reaches the literal-only overload, which throws NotSupportedException. The guard cannot fire in the configuration it was written for.

5 · One constant-expression evaluator behind one interface

Worth exploring in-process
  • src/xStunit.Interpreter/Loaders/StructBoundaryBuilder.cs :131-166 — a second evaluator
  • src/xStunit.Interpreter/Engine/Engine.Defaults.cs :89, :114-118, :133-145
  • src/xStunit.Interpreter/Engine/Engine.SizeOf.cs :36
  • src/xStunit.Interpreter/Types/TypeLayout.cs :134, :463-477
  • src/xStunit.Interpreter/Values/StringTypeInfo.cs :72-75

Before — the same rule, four times

After — one module, two adapters

Problem

"What does cCfg.MAX_ITEMS * 2 mean" has two independent implementations that can drift, and string capacity is resolved in four places with three different failure policies. The _resolveBound callback is the one point where layout re-enters the Engine — unguarded against recursion and uncached, so packing ARRAY[0..99] OF ST_Big recomputes every field size 100 times.

Solution

One ConstantResolver module answering bound, capacity and element count, with two adapters: the load-time GVL one StructBoundaryBuilder needs, and the run-time Frame one the Engine supplies. Recursion guard and memoisation land inside it, once.

Wins

  • Two evaluators become one
  • One failure policy for unresolved constants
  • Memoisation kills the O(n·fields) repack
  • Recursion guard has somewhere to live

7 · A fixture-engine module for the interpreter tests

Speculative in-process
  • tests/xStunit.Interpreter.Tests/ — 202 new Engine( sites, ~40 bespoke factories
  • tests/xStunit.Interpreter.Tests/Miniload/Miniload{Conveyor,Sensor,PackML}FixtureEngine.cs — forks WorkspaceLoader
  • src/xStunit.Interpreter/Loaders/WorkspaceLoader.cs :15 — all-or-nothing
  • src/xStunit.Interpreter/Engine/Engine.cs :30 — new Clock() hardcoded

Before — 40 factories, one production caller

After — one builder, the factories collapse into it

Problem

Every test file builds its own Engine setup from embedded ST source strings with \n\t escapes. Three fixture engines fork WorkspaceLoader because it is all-or-nothing — it returns the skip/error reporting a CLI needs and a test doesn't — and each fork silently omits GvlLoader and InterfaceLoader. The cost is real: LayoutChecklistPackWriteTests uses the 2-arg constructor, so the pack-write half of the conformance checklist is never exercised on x64.

Solution

One EngineFixture builder in the test project, wrapping WorkspaceLoader rather than forking it, with target platform as a first-class option. Marked Speculative: it touches ~40 call sites for no production change, so it earns its place only alongside a candidate that is already moving those tests — candidate 1 or 2.

Wins

  • x64 coverage stops being opt-in-by-accident
  • Fixture engines stop forking the loader
  • Leverage: one setup, N tests
  • New interpreter test costs 3 lines

Top recommendation

1 · Give the byte view a module of its own

Engine.ByteLayout.cs is the most-changed source file in the last 80 commits and the one place where layout knowledge has leaked back into the interpreter it was pulled out of. Deepening it is small — one module, four loops collapsed, one string compare replaced by SizeOf(elementType) == 1 — and it pays immediately: the SINT/USINT inconsistency disappears, Engine.SizeOf.cs stops being a shallow forwarder, and the byte-level tests get an interface to hit that isn't parsed ST.

Then candidate 2 — moving the layout oracle out of the shipped assemblies is nearly mechanical, sheds ~780 lines, and the two land in the same area of the tree.
